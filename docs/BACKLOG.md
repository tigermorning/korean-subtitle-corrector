4. **제44항 수 표기("몇만/몇백만") 자동교정 승격** — **확인: "몇만"·"몇백만"에 대한 코드·테스트 0건.** 이전 기록의 "현재 플래그만"은 부정확하다. 플래그도 없고 아무 처리도 없다. 제44항 관련 기존 테스트는 `tests/test_engine.py:286`의 "20만 명"을 쪼개지 않는지 확인하는 것뿐이라 이 항목과는 별개다.

15. **조사 '에서'를 '에'+'서다'로 갈라놓는 과교정 — 해결(2026-08-02)**. 원인은 kiwi 1순위 분석이 '에'(조사)+'서'(서다)였던 것. 대안 후보에 '에서'(조사 하나)가 있으면 자동으로 갈라놓지 않는다(`_merged_particle_reading_exists`). 아래는 발견 당시 기록이다. — 2026-08-02 `docs/IMPLEMENTATION_LOG.md` §37 작업 중 부수적으로 발견. `개나리길 입구에서 봐` -> `개나리길 입구에 서 봐`로 자동 교정된다(자동 교정 로그에 남음, 플래그 아님). `에서`는 한 덩어리 부사격 조사라 갈라선 안 된다. 어느 함수가 만드는지부터 확인할 것(`correct_particle_spacing`/`_mechanical_respace` 부근으로 추정). 자동 교정이라 사람이 못 보고 지나칠 수 있어 우선순위가 낮지 않다.
16. **거리 이름 `대로/로/가` 띄어 쓴 표기 자체를 플래그할지 결정** — 2026-08-02 `docs/IMPLEMENTATION_LOG.md` §37에서는 혼용이 있을 때 통일 후보를 고르는 데만 이 규칙을 썼다. `세종 대로`가 문서에 한 번만 나오면 지금은 아무 말도 하지 않는다. 규정상 붙임이 원칙이라 플래그할 근거는 있지만, `대로`가 일반명사로 쓰인 경우(`왕복 8차선 대로`)와 구분할 방법을 먼저 정해야 한다.

18. **사전 미등재 고유명사 분리 오탐(`한짓골` -> `한 짓골`) — 해결(2026-08-02)**. 아래는 해결 전 기록이다. `한`이 관형사(MM)로 태깅돼 `_TERM_COMPOUND_TAGS` 보호에서 빠진다. 사전에 없는 지명이라 사전으로는 방어할 수 없고, 현재 수단(고유명사 입력칸, 3회 이상 반복 자동 인식)은 사극처럼 한 번만 나오는 지명에 안 걸린다. **검토안**: 분리 제안이 만드는 조각이 전부 사전에 없으면 제안하지 않는다(`짓골` 미등재 -> 취소). 정당한 분리에도 사전에 없는 조각이 생기는 경우가 있어(활용형·조사 결합) 회귀 위험 측정이 선행이다.

19. **느낌표 뒤 띄어쓰기 제안 — 원인 규명·해결(2026-08-02)**. 느낌표가 아니라 감탄사 오분석이었다(`에라이!` -> `에라,이!`). 아래는 재현 실패 당시 기록이다. — 사용자가 "구두점은 늘 글자 바로 뒤에 온다"며 오탐을 보고했으나 `야! 이리 와`·`정말 대단해!`에서 재현되지 않았다. 원문(문장부호·앞뒤 문맥 포함)을 받으면 다시 볼 것. 같은 날 `말라 그래`도 마침표가 있어야만 재현됐다 — **오탐 재현은 사용자가 본 원문 그대로 넣어야 한다.**

### 외부 요인 대기 / 규모 큼

5. **`search_dialect()` — 확인 완료(2026-07-27), 우리 쪽 작업 없음** — 서버측 500 장애가 지속된다. 원 요청(`requests.get`)으로 `정구지`·`머스마`·`무싯날`·`감자` 4개 질의를 보냈고 **전부 HTTP 500 + HTML 오류 페이지**를 받았다. 기존 문서 기록("non-JSON 반환으로 사실상 중단")이 맞았다 — 앞서 이 항목에 "상태가 문서와 다르다"고 적은 것은 오판이었다. `search_dialect()`가 실패를 삼키고 `[]`를 돌려주는 것을 "정상 응답, 매칭 없음"으로 잘못 읽었기 때문이다. **상태 확인은 반드시 원 요청으로 할 것.** 서버가 복구되기 전에는 할 일이 없다.
6. **표준국어대사전 사전 내용 API(`view.do`)** — **확인: 코드 0건.** 용례·`norm_info`(한글 맞춤법 근거) 확인용. 근거 품질을 올릴 여지.
7. **온라인가나다 연동 2단계** — **확인: 코드 0건**(`docs/GRAMMAR_PRECEDENTS_TABLE.md` 문서에만 `qna_seq` 언급). 남은 작업 중 최대 규모. 깔끔한 API가 없어 검색/크롤링 방법 조사부터 필요(§8).
8. **클라우드 배포 — 종결(2026-08-02, 사용자 결정: 하지 않는다)**
   - **결정**: GitHub에 커밋·푸시만 제대로 하고, 실행은 로컬(`uvicorn` 또는 CLI)에서 한다. 유료 전환도, 다른 호스팅(HuggingFace Spaces 등) 이전도 하지 않는다.
   - **근거(2026-08-02 재확인)**: `https://korean-subtitle-corrector.onrender.com/`은 `GET /`가 200(정적 HTML이라 메모리를 안 씀)이지만 `POST /api/correct`는 **502**다. 2026-07-22 진단과 동일 — kiwipiepy 모델 약 310MB에 무료 티어 512MB라 교정 요청 시 한도를 넘는다. 설정 문제가 아니라 자원 한계라 코드로 우회할 수 없다(지연 로딩은 기동만 통과시키고 첫 교정에서 같은 한도에 부딪힌다). kiwi를 빼는 선택지도 없다 — 이 프로젝트의 모든 판정이 kiwi 형태소 태그 위에 서 있다.
   - **남아 있는 사실**: 그 URL은 2026-07-26~08-02 사이 커밋으로 떠 있어 최신 UI(띄어쓰기 기준 선택, 혼용 감지, 접기 패널)가 반영돼 있지 않다. 살아 있는 것처럼 보이지만 교정은 되지 않는 상태다. **이 URL을 동작하는 데모로 안내하지 말 것.** 배포를 되살리기로 마음이 바뀌면 이 항목부터 다시 열 것.

17. **교정 강도 선택(보수적/일반/리라이팅) — LLM 연동 전까지 보류(2026-08-02, 사용자 결정)**
    - **사용자가 정의한 3단계**: 보수적 = 기술적 교정 위주, 화자의 발화 자체는 바꾸지 않음(자막이나 보수적 교정을 요구한 문서). 일반 = 자연스러운 표현 제안·문장 구조 개선 허용. 리라이팅 = 문체 변경·문단 재구성까지 허용.
    - **왜 지금 못 만드나**: 이 엔진은 표준국어대사전·우리말샘·어문 규범을 조회해 **규범 위반 여부**를 판정한다. "이 표현이 자연스러운가", "이 문장 구조가 나은가", "이 문단을 어떻게 재구성할까"는 사전에 답이 없어 규범 조회로 도달할 수 없다. 일반·리라이팅은 기능 범위를 넓히는 일이 아니라 **없는 능력을 새로 붙이는 일**이다.
    - **필요한 것**: LLM(Claude API 등) 연동. 아키텍처 변경이라 API 키·비용과 함께, "확률적 추측으로 자동 수정하지 않는다"(`PRD.md` §5)는 최우선 원칙과 어떻게 공존시킬지 먼저 정해야 한다 — 최소한 제안 전용으로 못 박고 자동 교정 경로에는 절대 연결하지 않는 선.
    - **보수적 단계만은 지금도 가능하다**(참고용 설계, 착수 승인 안 받음): 어휘를 바꾸는 교정(비표준어·차별적 표현·옛 용어 치환)을 자동 적용 대신 확인 플래그로 강등하고, 표기 교정(띄어쓰기·맞춤법·외래어 표기·자막 부호)은 자동 유지. 기준선은 "표기를 고치는가 / 화자가 고른 낱말을 바꾸는가"다. 다만 세 단계를 함께 내놓지 못하면 반쪽이라, 사용자가 LLM 연동 전까지 강도 설정 자체를 만들지 않기로 했다.
