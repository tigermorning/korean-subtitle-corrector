# 설계 원칙 — 피드백을 사례별 패치가 아니라 공유 원리로

이 교정기는 **룰 기반 시스템**이다(스스로 학습하는 신경망이 아님). 따라서 "정보가
없어서" 오탐하는 게 아니라, **가진 사전·규범 정보를 조회·판정하는 로직**이 그
정보를 잘못 걸러낼 때 오탐한다(예: `word_exists`가 표준국어대사전 등재를 우리말샘
비표준 동형이의어 때문에 무시하던 버그 — `docs/IMPLEMENTATION_LOG.md` §33).

## 오탐·과교정은 대개 4가지 원리의 반복 위반이다

새 피드백을 받으면 **먼저 아래 분류부터** 한다. 대부분 개별 사례가 아니라 이
중 하나의 반복이다.

1. **조각 대조 (fragment-flagging)** — kiwi가 쪼갠 토막만 사전 대조하고, 그
   토막을 포함하는 **최대 사전-유효 구간**을 확인하지 않아 유효 단어를 오탐.
   예: 얄짤(→얄짤없다), 껄쩍(→껄쩍지근하다), 김치찌갯(→김치찌갯집), 수강(→수강생).
2. **모호할 때 자동 교정** — 정답이 하나로 확정되지 않는데 자동 교정.
   예: 보물선/선투자, 본 집/본집. **원칙: 자동 교정은 정답이 100% 하나일 때만.**
3. **우연한 사전 충돌** — 인접 조각을 이어붙인 문자열이 무관한 표제어와 겹침.
   예: 집→지브, 어+하다=어하다, 오고+하다=오고하다. 반드시 **온전한 어휘 단위**
   (어간+어미, 합성어 양쪽)로 확인하고 우연한 부분 문자열로 판단하지 않는다.
4. **조회 로직 버그** — 가진 데이터를 잘못된 판정으로 버림.
   예: 흩어지다(word_exists가 혼합 표제어를 통째 비표준 처리).

## 수정 워크플로: 인스턴스가 아니라 공유 가드를 고친다

리포트 1건 → 패치 1건은 같은 부류 버그가 계속 재발한다. 대신:

1. **분류** — 위 1~4 중 어디인가? (또는 진짜 새 규칙인가?)
2. **원리 1~4면 공유 가드를 고친다** — 그 부류 전체가 한 번에 커버되게.
   (예: `word_exists` 한 번 수정으로 흩어지다류 전부 해결.)
3. **진짜 새 규칙이면** `grammar-rule-verify-then-code` 절차로 사전 검증 후
   정답표(코드+테스트)에 추가한다.
4. **회귀 고정** — 모든 수정은 `tests/test_realusage_review.py` 정답표에 케이스를
   추가하고, 매 변경마다 전체 스위트 + `examples/eval/run_eval.py`(held-out)를
   돌려 "한 사례 고치다 다른 사례 깨는 것"을 차단한다. 이 누적 테스트가 이
   시스템의 실질적 "기억"이다.

## 수렴 리팩터링 목표(권장 순서)

지금은 원리 1(조각 대조) 억제 로직이 `_unknown_content_words`(첩어·의성어·
용언 lemma·고유어 합성어·된소리 변이), `check_former_terms`(XSN 접미사),
`check_spacing`(`_protect_headword_run_splits`) 등에 흩어져 있다. 다음을 목표로 한다.

1. **표제어 조회 중앙화** — "이 토큰을 오류로 판정하기 전에 그것을 포함하는 최대
   사전-유효 구간을 확인" 하는 단일 함수를 만들고 모든 검사가 호출. 원리 1
   버그 부류를 통째로 제거.
2. **auto vs flag 단일 정책** — "교정형이 유일한 사전-유효 결과일 때만 자동,
   아니면 플래그"를 하나의 게이트로. 지금은 각 교정 함수가 따로 판단해 구멍이 생김.
3. **held-out eval을 상시 지표로** — 사례별 패치가 실제 정확도를 올리는지 수치로 확인.

## "학습"의 현실적 의미

피드백은 둘 중 하나가 된다: (i) 공유 가드 버그를 드러냄 → 한 번 고쳐 부류 전체
개선(진짜 일반화), (ii) 검증된 규칙 하나를 정답표에 추가 → 영구 가드로 고정.
held-out eval이 "실제로 나아지는가"를 수치로 답한다.
