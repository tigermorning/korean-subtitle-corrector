# 자막 편집기 프로젝트 브리프 (별도 프로젝트)

작성일: 2026-08-11
근거: SE 실사용자(본 프로젝트 소유자)의 페인 포인트 4건 + SubtitleEdit 코드 실측
관련 문서: `SUBTITLEEDIT_ARCHITECTURE_ANALYSIS.md`, `SUBTITLE_GUIDE_SDH.md`, `SUBTITLE_GUIDE_TRANSLATION.md`

## 1. 제품 분리 원칙 (결정됨)

| | **한국어 교정기** (현 프로젝트) | **자막 편집기** (신규 프로젝트) |
|---|---|---|
| 대상 | 일반 사용자 | 전문 번역가 · 자막 작업자 |
| 성격 | 범용 한국어 교정 도구 | 전문 납품 도구 |
| 자막 지식 | **없어야 함** | 전부 여기 |
| 관계 | **엔진(라이브러리)** | 엔진을 **소비하는 애플리케이션** |

**이유**: 자막 전용 설정·규정이 교정기에 쌓이면 일반 사용자에게 쓸모없는 복잡도가 된다. 교정기는 얇고 범용으로 유지하고, 자막 도메인 지식은 전부 편집기 쪽에 둔다.

### 경계선 규칙

| 어디에 두나 | 판별 기준 | 예 |
|---|---|---|
| **교정기** | 자막이 아니어도 성립하는 순수 한국어 지식 | 맞춤법, 띄어쓰기, 조사/어미, 외래어 표기, 방언, 어휘 일관성, 문장 부호 일반 |
| **편집기** | 타임코드·화면·플랫폼 규정을 알아야 성립하는 것 | CPS, 줄당 글자 수, 줄바꿈 위치, 화자 표시 `[ ]`, ♪, 강제 자막, 넷플릭스/디즈니 프로파일, 싱크 |

**회색 지대 판정법**: "이 규칙을 이메일 원고에 적용해도 말이 되는가?" 되면 교정기, 안 되면 편집기.

### ⚠️ 이미 침투가 시작됐다

교정기 코드에 자막 도메인이 이미 들어와 있다. 지금 표시해두면 나중에 이전이 싸다.

| 위치 | 내용 | 판정 |
|---|---|---|
| `subtitle_corrector/engine/subtitle_rules.py` | 자막 전용 규칙 | → 편집기로 이전 대상 |
| `subtitle_corrector/formats.py` | vtt/smi/ass/sbv/ttml/subviewer 파서·라이터 | → 편집기로 이전 대상 (libse와 중복) |
| `subtitle_corrector/parsers.py` | 자막 엔트리 파싱 | → 검토 |
| `api.py` `get_speakers()` | 화자 추출 | → 편집기로 이전 대상 |
| `SubtitleEntry` 자료형 | 타임코드 포함 | → 교정기 코어는 순수 텍스트만 받도록 정리 |

**지금 당장 뜯을 필요는 없다.** 교정기 완성이 먼저다. 다만 **새 자막 기능을 교정기에 더 넣지 않는 것**은 지금부터 지킨다.

## 2. 페인 포인트 → 코드 실측 → 대응

### P1. 타임코드를 수동으로 해야 한다

**SE 현황 (있는 것)**
- `libse/Forms/TimeCodesBeautifier.cs` — 타임코드 정돈
- `libse/Forms/DurationsBridgeGaps.cs` — 갭 브리징
- `libse/Common/ShotChangeHelper.cs`, `ui/Features/Video/ShotChanges/*` — **샷 체인지 검출 있음**
- `FixShortDisplayTimes`, `FixLongDisplayTimes`, `FixOverlappingDisplayTimes`, `FixShortGaps`

**진짜 문제**: 기능이 없는 게 아니라 **전부 사람이 메뉴를 눌러 하나씩 돌려야 하고, 어떤 순서로 무엇을 돌려야 하는지 도구가 모른다.** 프로파일(넷플릭스 ko SDH 등)을 걸면 자동으로 "샷 체인지 스냅 → 최소/최대 길이 → 갭 → CPS 최적화"가 한 번에 수렴하는 파이프라인이 없다.

**대응**: 프로파일 기반 **타임코드 수렴 파이프라인**. 규칙 간 충돌(예: CPS 맞추려 늘리면 갭 위반) 해소 순서를 명시하고, 수렴 결과와 남은 위반을 리포트로 출력.
**난이도**: 중. libse 부품이 이미 다 있어서 오케스트레이션 문제다.

### P2. Whisper에 검수가 없고 맥락을 놓친다

**SE 현황**
- `libuilogic/AudioToText/` — 엔진 4종 래핑(whisper.cpp, ConstMe, CTranslate2, Purfview Faster-Whisper)
- **후처리 언어 지원은 `GermanNouns.cs` 단 하나.** 독일어 명사 대문자화가 전부다
- 검수 계층 없음. 신뢰도 노출 없음. 화자 분리 없음. 용어집 주입 없음

**진짜 문제**: 받아쓰기가 **단발 실행 + 결과 그대로 신뢰**다. 맥락 상실(인명·고유명사·존댓말 흔들림·문장 경계 오류)을 잡을 장치가 0.

**대응**:
- 용어집/화자 목록을 프롬프트로 주입 (인명·고유명사 고정)
- 2-pass: 초벌 받아쓰기 → 구간별 재검증(신뢰도 낮은 구간만 재실행)
- 세그먼트 신뢰도 시각화 → 사람이 볼 곳을 지정
- 화자 분리(diarization) 결과를 SDH 화자 표시 후보로 연결
- 받아쓰기 결과에 **교정기를 바로 물려** 맞춤법·존댓말 일관성 정리

**난이도**: 상. 이 프로젝트의 핵심 차별점이 될 가능성이 제일 큰 항목.

### P3. 가이드를 사람이 외워서 적용해야 한다

**SE 현황**
- `ui/Logic/NetflixQualityCheck/` 체크 17종. **ko 수치는 정확하다** (16자 / 번역 12·9 CPS / SDH 14·11 CPS, `IsSDH` 플래그 존재)
- 그러나 **표기 규칙은 0건**. 줄 끝 마침표 금지, 따옴표 역할 구분, `[외국어로 말한다]` 금지, 효과음 어미, ♪ 공백, 화자 표시 일관성, 삐 처리 음절 수 — 전부 없음
- 디즈니+·쿠팡 프로파일 없음
- 위반을 지적할 때 **근거 조항을 못 댄다**

**대응**: 규정을 **데이터로** 정의. 위반 리포트에 조항 번호를 함께 출력 (`Korean TTSG I.13 — 줄 끝 마침표 금지`). 이미 `SUBTITLE_GUIDE_*.md` 두 문서에 T1~T17 / S1~S14로 룰 후보가 정리돼 있다.
**난이도**: 중하. 데이터 작업이 대부분. **가장 빨리 체감 가치가 나오는 항목.**

### P4. 자막 교정 기능이 없다

**SE 현황**
- `FixCommonErrors` 40여 종 — 전부 영어권 규칙(아포스트로피, 문장 첫 대문자, 덴마크어 i, 터키어 인코딩 등)
- `Dictionaries/` 에 **한국어 사전 0개**. `ko_NoBreakAfterList.xml` 없음
- `Utilities.AutoBreakLinePrivate`은 `IsCjkLanguage(ko)`면 어절 분리 경로를 아예 타지 않음 → 한국어 줄바꿈이 글자 수 절단 수준

**대응**: 교정기를 엔진으로 붙인다. 이 항목은 **이미 만들어놓은 자산이 그대로 답이 되는 유일한 항목**이다.
**난이도**: 하(엔진 재사용) + 중(줄바꿈은 신규 — 조사·의존명사 인식 필요, 교정기의 `engine/spacing.py`·`dependent_nouns.py`·`kiwi_adapter.py` 활용 가능)

## 3. 재사용 자산 정리

### 교정기에서 가져다 쓸 것
- `subtitle_corrector/engine/pipeline.py` + `options.py` — 교정 파이프라인 진입점
- `engine/spacing.py`, `spacing_guards.py`, `dependent_nouns.py`, `affix.py` — **한국어 줄바꿈의 핵심 재료**
- `engine/consistency.py` — 용어 일관성 (자막에서는 화자 표시·인명 일관성으로 확장)
- `engine/kiwi_adapter.py` — 형태소 분석
- `report.py`의 `FlagItem` / `AppliedNote` — 리포트 계약. 편집기 리포트도 같은 모양으로 맞추면 통합이 쉽다

### libse에서 가져다 쓸 것
- 자막 포맷 408종 파싱/쓰기 (교정기 `formats.py`를 대체 가능)
- 컨테이너 파싱, OCR, Blu-ray/VobSub
- 샷 체인지 검출, 타임코드 유틸
- `RulesProfile`, `ICalcLength`/`CalcCjk`, `IFixCommonError` 확장점

## 4. 연동 방식 후보 (미결정)

| 안 | 구성 | 장점 | 단점 |
|---|---|---|---|
| A | 편집기 C#(.NET) + 교정기를 로컬 HTTP 서비스로 호출 | libse 네이티브, 교정기 `api.py`(FastAPI) 이미 존재 | 프로세스 2개, 배포 복잡 |
| B | 편집기 C# + 교정기를 CLI(JSON in/out)로 호출 | 단순, 배포 1벌 가능 | 호출 오버헤드, 대용량 시 느림 |
| C | 편집기도 파이썬 + libse는 `seconv` CLI로만 사용 | 한 언어, 교정기 직접 import | libse 기능 대부분(샷체인지·OCR·Whisper 래핑) 못 씀 |

**판단 요소**: 자막 편집기는 GUI + 미디어 재생 + 파형이 필요하다. 이게 언어 선택을 사실상 결정한다. 결정 전에 UI 스택부터 정하는 게 순서다.

## 5. 진행 순서 (결정됨)

1. **한국어 교정기 완성** ← 현재 단계. 자막 기능 추가 동결
2. 교정기 공개 API 계약 안정화 (편집기가 부를 표면 확정)
3. 자막 편집기 저장소 개설 + 이 문서 이전
4. 편집기 착수 — 우선순위: **P3(규정 자동 적용) → P4(교정 연동) → P1(타임코드 파이프라인) → P2(Whisper 검수)**
   - P3가 가장 싸고 체감이 크다. P2는 가장 비싸지만 차별점이 가장 크다
